# RF-01 — Patient Access Market Requirement Audit

## Objective

Build a defensible employer-side baseline for entry-level Patient Access roles before evaluating Kori's portfolio evidence.

**Target sample:** 10–15 current Patient Access postings.

This phase is research-only. Do not score Kori's evidence, calculate student-evidence coverage, or create new portfolio projects during this phase.

---

## Primary Titles to Search

- Patient Access Representative
- Patient Registration Representative
- Registration Representative
- Patient Access Specialist
- Patient Access Coordinator
- Patient Services Representative when the duties are clearly registration / access oriented

Do not include a posting based on title alone. Review the actual responsibilities and requirements.

---

## Primary Sample Filters

A posting should be marked as a **qualified market-sample posting** only when the available evidence supports all applicable criteria:

| Filter | Required Status |
|---|---|
| Remote arrangement | Explicitly 100% remote |
| Tennessee eligibility | Verified eligible or nationwide with no Tennessee exclusion |
| Onsite requirement | No mandatory onsite training or recurring onsite work |
| Posting status | Active when reviewed |
| Source legitimacy | Official employer career site preferred |
| Entry-level accessibility | 0–1 year preferred; otherwise record exact experience requirement and classify accordingly |

Postings that fail one of these filters may be retained as **supplemental market intelligence**, but they must be clearly marked and should not silently inflate the qualified sample.

---

## Posting IDs

Assign postings sequentially:

- PA-J01
- PA-J02
- PA-J03
- ...
- PA-J15

Do not reuse an ID for a different posting.

---

## Raw Intake Fields

Each posting must capture:

1. Posting ID
2. Employer
3. Exact job title
4. Source URL
5. Date reviewed
6. Posting active status
7. 100% remote status
8. Tennessee eligibility status
9. Onsite training status
10. Minimum experience — exact wording
11. Education requirement — exact wording
12. Requirement text — original employer language
13. Required or preferred
14. Technology mentioned
15. Workflow responsibility
16. Communication responsibility
17. Sample classification
18. Notes

---

## Requirement Preservation Rule

For every requirement, preserve the employer's original wording before interpretation.

Example:

> Verifies patient demographic and insurance information and updates records as necessary.

Do **not** replace this during raw collection with a normalized label such as `Registration / Demographic Data Accuracy`.

Normalization occurs only after the employer sample has been collected.

---

## Requirement Type Classification

After raw collection, classify each requirement using one of these types:

- Hard Qualification
- Technical Skill
- Workflow Competency
- Knowledge
- Communication
- Preferred Qualification

Examples:

| Employer Requirement | Requirement Type |
|---|---|
| 2 years of patient-access experience | Hard Qualification |
| High school diploma or equivalent | Hard Qualification |
| Microsoft Excel | Technical Skill |
| Verify patient demographics | Workflow Competency |
| Communicate professionally with patients | Communication |
| Prior authorization knowledge preferred | Knowledge / Preferred Qualification |

A hard professional-experience requirement must remain a qualification issue. It cannot be converted into a student portfolio competency.

---

## Normalization Rule

Only after the raw sample is sufficiently populated should similar employer phrases be grouped into normalized competencies.

Example:

| Employer Language | Normalized Competency |
|---|---|
| Verify patient demographics | Registration / Demographic Data Accuracy |
| Confirm patient information | Registration / Demographic Data Accuracy |
| Update demographic information | Registration / Demographic Data Accuracy |
| Maintain accurate registration records | Registration / Demographic Data Accuracy |

The original employer wording must remain traceable to the normalized competency.

---

## Market Frequency Rule

After normalization, calculate how often each competency appears across the qualified market sample.

Use:

`Market Frequency = Number of qualified postings mentioning competency / Total qualified postings reviewed`

Do not use supplemental or personally ineligible postings in the primary frequency denominator unless the methodology explicitly says so.

Do not describe market frequency as a qualification probability.

---

## Current Completion Gate

RF-01 employer-side baseline is ready for the next phase only when:

- [ ] 10–15 postings have been reviewed
- [ ] each posting has a unique Posting ID
- [ ] source and review date are recorded
- [ ] remote status is verified or marked unclear
- [ ] Tennessee eligibility is verified or marked unclear
- [ ] onsite training is verified or marked unclear
- [ ] experience and education language are preserved
- [ ] original requirement language is preserved
- [ ] required vs. preferred status is captured where available
- [ ] qualified vs. supplemental sample classification is assigned
- [ ] similar requirements have been normalized only after collection
- [ ] market frequency has been calculated from the qualified sample

Only after this gate passes should the system begin auditing Kori's personal evidence.

---

## Student / Portfolio Boundary

This market audit does not claim employment experience or professional Patient Access authority.

It exists to identify what employers request so later portfolio evidence can be crosswalked honestly and selectively.
